# تقرير المراجعة والإصلاحات — AI Marketing Agent (WhatsApp)

هذا تقرير كامل بكل مشكلة انلقت بالأتمتة الأصلية (`AI_Marketing_Agent_-_WhatsApp_____.json`)، وشلون انصلحت
بالنسخة الموجودة بـ `workflows/ai-marketing-agent-whatsapp.json`. كل الإصلاحات انختبرت منطقياً بـ Node.js
خارج n8n (سكربتات الاختبار داخل نفس commit تحت مجلد مؤقت، والنتائج ملخصة تحت).

## 1، 2، 3 — تسريب بيانات واختيار حساب غلط (الأخطر بالأتمتة)

**قبل:** نود `جلب حساب العميل` كان يجيب **كل** صفوف شيت "العملاء" (كل العملاء، مو بس عميل المرسل) بدون
أي فلتر. بعدين كود `تحقق قبل التنفيذ` كان يقرر:
- إذا فيه أكثر من صف بالشيت كله → يرسل للمستخدم قائمة **بكل** حسابات كل العملاء (تسريب مباشر).
- إذا فيه صف وحد بس بالشيت كله → يستخدمه تلقائياً، حتى لو مو عميل المستخدم اللي حجى!

نفس المشكلة بالضبط بنود `جلب الحالة المعلقة`: كان ياخذ أول صف موجود بالشيت، مو صف نفس رقم الهاتف،
يعني ممكن محادثة مستخدم "أ" تختلط بمحادثة مستخدم "ب".

**بعد:** أضفنا دالة `normalizePhone()` بكل نود Code يهمه رقم الهاتف (تشيل الرموز وتاخذ آخر 10 أرقام،
حتى تتطابق أرقام مكتوبة بصيغ مختلفة مثل `07811317191` و`+9647811317191` و`9647811317191`). وبعدين:
- `تجهيز سياق الـAI` يدور على الصف اللي `phone` بيه يطابق رقم المرسل بالضبط.
- `تحقق قبل التنفيذ` يفلتر حسابات "العملاء" على رقم المرسل أولاً، وبعدين على اسم العميل (إذا انذكر
  بالرسالة) لو المرسل نفسه يدير أكثر من عميل.

**اختبرناها:** سيناريو فيه 3 عملاء بالشيت (وحد يخص رقم المرسل، واثنين يخصون أرقام ثانية) — النتيجة
اختارت حساب المرسل فقط، وما ظهرت أي بيانات عن العملاء الثانين برسالة الرد. ✅

## 4 — حذف كان يقدر يمسح الشيت كامل

**قبل:** نود `حذف الحالة المعلقة` كان `operation: delete` **بدون تحديد أي صف أو فلتر**. عملية Delete
بجوجل شيتس بتمسح حسب رقم صف (index)، مو حسب قيمة عمود — فبدون تحديد الصف، النتيجة غير مضمونة وممكن
تمسح صفوف مو المفروض تنمسح، أو الشيت كامل.

**بعد:** حولناها لعملية `appendOrUpdate` (نفس أسلوب الحفظ المستخدم بباقي الأتمتة) تصفّر عمود
`draft_json` لصف رقم الهاتف نفسه بس (`matchingColumns: ["phone"]`)، فتصير "تصفير" آمن بدل "حذف" خطر.
غيّرنا اسم النود لـ **"تصفير الحالة المعلقة"** ليعكس الوظيفة الجديدة.

## 5 — appendOrUpdate بدون matchingColumns

نودات حفظ الحالة المعلقة (الناقصة، وبانتظار تأكيد) ما كان فيها `matchingColumns`، وهذا الحقل **إلزامي**
لعملية Append or Update حتى تعرف جوجل شيتس أي عمود تستخدمه للمطابقة قبل ما تقرر تحدّث الصف الموجود أو
تضيف صف جديد. بدونه، الاحتمال الأرجح إنه يضيف صف جديد كل مرة بدل ما يحدّث، ويتكدس الشيت بمئات الصفوف
المكررة لنفس الرقم. أضفنا `matchingColumns: ["phone"]` للنودين + النود الجديد "تصفير الحالة المعلقة".

## 6 — TikTok: عمليتين كاملتين مو موجودتين

Switch الخاص بـ Meta فيه 6 قواعد (إنشاء، تفعيل، إيقاف، تعديل ميزانية، حذف، تقرير). أما Switch
TikTok فكان فيه **4 قواعد بس** (إنشاء، تفعيل، إيقاف، تقرير) — يعني لو مستخدم كتب
"غيّر ميزانية حملة التيك توك" أو "احذف حملة التيك توك"، الأتمتة توصل لنقطة الـ Switch وما تلقى قاعدة
تطابق، فتتوقف بصمت تام — ولا حتى رسالة خطأ توصل للمستخدم.

**الحل:** أضفنا نودين جدد:
- `TikTok: تعديل الميزانية` (endpoint: `campaign/update/`)
- `TikTok: حذف حملة` (endpoint: `campaign/status/update/` بقيمة `operation_status: DELETE`،
  لأن TikTok ما عنده حذف نهائي حقيقي، بالضبط متل أسلوب `ARCHIVED` المستخدم مع Meta)

وأضفنا قاعدتين جديدتين بالـ Switch بنفس ترتيب Meta بالضبط.

⚠️ **ملاحظة مهمة:** هذولا endpoints مبنية حسب توثيق TikTok Business API المعروف وقت كتابة هذا التقرير،
لكن TikTok يغيّر تفاصيل الـ API أحياناً (مثلاً هل الميزانية تنضبط على مستوى الحملة أو الـ Ad Group حسب
إعداد حسابك). **جرّبها أول مرة بحملة تجريبية بميزانية صغيرة قبل ما تعتمد عليها بحملات حقيقية.**

## 7 — رسائل خطأ موجودة لكن معزولة تماماً

نودين `رد: إجراء Meta غير معروف` و `رد: إجراء TikTok غير معروف` كانوا موجودين بقائمة نودات الأتمتة
لكن **غير موصولين بأي نود ثاني إطلاقاً** — يعني حتى لو كانت الأتمتة تتوقع تستخدمهم كرسالة خطأ احتياطية،
عملياً ما كان فيه أي مسار يوصّلها لهم. أضفنا `fallbackOutput: extra` لكل Switch ووصلناهم كمخرج أخير،
فأي إجراء غير متوقع الآن يرجع للمستخدم رسالة خطأ واضحة بدل السكوت التام.

## 8 — قائمة الأرقام المصرح لها

**قبل:** الأرقام المسموحة كانت مكتوبة حرفياً جوة شرط IF (`['9647811317191', '07811317191', ...]`).
لإضافة زبون جديد لازم تفتح الأتمتة وتعدّل الكود يدوياً — غير عملي لموديل خدمة تسويقية لعدة عملاء.

**بعد:** أضفنا:
- نود `جلب قائمة المصرح لهم` يقرأ شيت جديد اسمه **"المستخدمين المصرح لهم"**
- نود Code جديد `تحقق الرقم من القائمة` يطابق رقم المرسل (بأي صيغة) مع الشيت، ويتأكد من عمود `active`
  (لو `false` معناها موقوف مؤقتاً بدون حذف صفه)
- نود IF `تحقق من الصلاحية` صار يعتمد على النتيجة الجاهزة `authorized` بدل قائمة مكتوبة بالكود

**الآن لإضافة زبون جديد:** تفتح الشيت وتضيف صف بس، بدون أي تعديل على الأتمتة. هذا يطابق فكرتك
بربط عدة عملاء بنظام واحد بدون ما تلمس الأتمتة كل مرة.

1. **جهّز 4 جداول Data Tables** بالأعمدة المذكورة بـ [docs/SETUP.md](./SETUP.md) (راجع بند 10 تحت
   ليش Data Tables بدل Google Sheets).
2. **افتح كل نود "Data table" (7 نودات) وأعد اختيار الجدول من القائمة المنسدلة مرة وحدة** — لأن كل
   حساب n8n عنده أرقام تعريف (ID) مختلفة لجداوله، والأرقام المكتوبة بالملف تخص حساب آخر.
3. **اختبر مسار TikTok (تعديل ميزانية / حذف) بحملة تجريبية أول** قبل الاعتماد عليه بحملات حقيقية،
   لاحتمال اختلاف تفاصيل الـ API البسيطة حسب إعداد حسابك.
4. القائمة البيضاء الآن بجدول "المستخدمين المصرح لهم" — لا تنسى تضيف رقمك ورقم أي شخص ثاني مصرح له
   قبل أول اختبار.

## 10 — من Google Sheets إلى Data Tables (تغيير جوهري)

**المشكلة اللي واجهناها:** بعد كل الإصلاحات أعلاه، جربنا الأتمتة فعلياً بحساب n8n Cloud حقيقي، ولقينا
مشكلة إضافية ما كانت واضحة من مراجعة الكود وحدها: نوع ربط Google المُدار تلقائياً من n8n ("Managed
OAuth2") كان يخلي الاتصال "ناجح" ظاهرياً (يقدر يعرض أسماء التبويبات بالقائمة المنسدلة)، لكن أي محاولة
فعلية لقراءة بيانات الصفوف كانت ترجع فاضية تماماً بدون أي رسالة خطأ — حتى بعد تجربة حسابين مختلفين
وإعادة الربط عدة مرات. هذا نوع مشاكل صلاحيات (OAuth scope) معروف بربط Google المُدار على بعض حسابات
n8n Cloud.

**الحل:** استبدلنا كل نودات Google Sheets السبعة (قراءة/كتابة) بنودات **Data Table** المدمجة داخل n8n
نفسها — ميزة مخزّنة محلياً بحساب n8n، بدون أي حاجة لربط حساب Google أو صلاحيات OAuth إطلاقاً. نفس
الوظيفة بالضبط من منظور المستخدم على واتساب، بس أبسط وأسرع بالإعداد وأكثر أماناً (بيانات العملاء ما
تطلع من حساب n8n إطلاقاً).

**التغييرات التقنية:**
- 7 نودات Google Sheets (`n8n-nodes-base.googleSheets`) تحولت لنودات Data Table (`n8n-nodes-base.dataTable`).
- عمليات القراءة (`جلب الحالة المعلقة`, `جلب حساب العميل`, `جلب قائمة المصرح لهم`) صارت `operation: get`
  مع `returnAll: true` — نفس منطق الفلترة على رقم الهاتف بنودات Code بقى بدون تغيير.
- عمليات الحفظ/التحديث (`حفظ الحالة المعلقة` × 2, `تصفير الحالة المعلقة`) صارت `operation: upsert`
  بمطابقة `phone` — تعمل تحديث أو إضافة تلقائياً بضغطة وحدة، وأبسط من appendOrUpdate بجوجل شيتس.
- `حفظ النتيجة` صارت `operation: insert` — رقم الصف والتاريخ يتولدون تلقائياً (id/createdAt) بدل ما
  نديرهم يدوياً متل الشيت.
- اختبرنا كل عملية فعلياً على حساب n8n Cloud حقيقي (مو بس منطقياً بـ Node.js) قبل التسليم — راجع
  محادثة الإعداد إذا تريد تفاصيل كل اختبار.
