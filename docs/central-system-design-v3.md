# وثيقة التصميم — الإصدار 3: مشروع جديد مستقل بالكامل

> **الحالة: خطة للمراجعة فقط. لم يُنفَّذ أي شيء.** لا مستودع جديد أُنشئ، ولا قاعدة، ولا خدمة، ولا موارد مدفوعة، ولا طلب صلاحيات خارجية، ولا اتصال بأي نظام قديم. بانتظار موافقتك على هذه الخطة.
> يحلّ محل v2 (نفس الملف بعد تعديل النطاق). الإصدار v1 يبقى أرشيفاً فقط (فيه تدقيق النظام القديم ووثائق ترحيله) ويخرج من نطاق المشروع.

## 0) قرار النطاق وتأكيد الاستقلال

**المشروع الجديد = نظام جديد كلياً، لا علاقة تشغيلية له بالنظام القديم.** البوتات الحالية (الرئيسي، علي، حسن، مسلم، أحمد، زيد، TEMPLATE) وWorkflows وجداولها وتوكناتها واتصالاتها وWebhooks ها **خارج المشروع تماماً**: لا نقرؤها، لا نعدّلها، لا نوقفها، لا نستوردها، ولا نبني عليها.

### التأكيد الصريح
**أؤكد أن المشروع الجديد لن يعتمد على أي مكوّن تشغيلي من النظام القديم.** بالتفصيل:

| المكوّن | في المشروع الجديد |
|---|---|
| مستودع الكود | مستودع **Git جديد** منفصل (تنشئه أنت أو تأذن لي بإنشائه). |
| خادم/استضافة | موارد جديدة بحساب/مشروع منفصل. **ليس** خادم Hostinger الحالي ولا Railway الحالي. |
| n8n | **نسخة n8n جديدة** مستقلة (Docker محلياً للتطوير، ثم نسخة مستضافة جديدة). **ليس** `n8n.srv2007124.hstgr.cloud`. |
| قاعدة البيانات | PostgreSQL **جديدة وفارغة**؛ الجداول (Data Tables) القديمة ال‑91 لا تُنسخ ولا تُقرأ. |
| Telegram | بوت **جديد** تنشئه أنت من BotFather خصيصاً للمشروع، بتوكن جديد؛ ومجموعة/محادثة تنبيهات جديدة. |
| TikTok / Meta | **تطبيقات مطوّرين جديدة** (App ID/Secret جديدان) وحسابات اختبار/Sandbox. **لا** نستعمل التطبيق الحالي (`app_id` القديم) ولا Redirect URI القديم. |
| الأسرار/المفاتيح | كلها تُولَّد من جديد (KEK، مفاتيح HMAC، سرّ ctx، كلمات سر الأدوار). لا توكن ولا سرّ منسوخ من القديم. |
| البيانات | وهمية فقط (عميلان تجريبيان). لا بيانات عملاء حقيقيين، لا حملات حقيقية. |

### ما يُقال بأمانة (حدود الاستقلال)
1. **الكود الأولي المكتوب في هذه الجلسة** (`design/central-db` و`design/broker`) كُتب من الصفر، وتحققتُ بالبحث النصي أنه **لا يحوي** أي معرّف أو توكن أو اسم عميل أو مسار أو Workflow من النظام القديم. لكنه موجود حالياً داخل **المستودع القديم** (فرع `claude/funny-volta-1s7cvn`) لأن الجلسة تعمل فيه. عند الموافقة: يُنقل إلى المستودع الجديد، ويُبنى من هناك فقط. وسأزيل ملفات `__pycache__` التي دخلت الـ commit بالخطأ.
2. **أداة n8n المتصلة بجلستي حالياً مربوطة بنسخة n8n القديمة.** لذلك **لن أستخدمها إطلاقاً** لهذا المشروع. الـ Workflows الجديدة تُكتب كملفات (JSON/كود) داخل المستودع الجديد، وتُختبر على n8n محلي (Docker)، وتُنشر على النسخة الجديدة عبر مفتاح API جديد خاص بها.
3. **ما لا يمكن فصله كلياً:** هويتك الشخصية كمالك (حساب Telegram الذي يفتح BotFather، وحساب المطوّر لدى Meta/TikTok). الفصل التشغيلي ممكن (تطبيقات وبوتات ومعرّفات منفصلة)، لكن سياسات المنصات تُطبَّق على الحساب المالك؛ لذلك أوصي بـ Business Manager/حساب مطوّر مخصص للمشروع حيث تسمح المنصة.
4. **المعرفة:** ما تعلمته من تدقيق النظام القديم (دروس وأخطاء تصميم) يؤثر على قراراتي التصميمية فقط، ولا ينتقل منه أي مكوّن أو بيان.

## 2) عزل العملاء (Tenant Isolation + RLS) — اقتراح **وتطبيق**

### الآلية (مطبّقة في `20_rls.sql` و`30_functions.sql`)
1. بوت تيليجرام لكل عميل → webhook على مسار فريد (`bot_public_id` ≥ 22 حرفاً) + `secret_token` يتحقق منه Postgres (مخزَّن كـ hash).
2. `api.resolve_context(bot_public_id, secret, telegram_user_id)` (دور `app_resolver` فقط) يتحقق ويُرجع **ctx موقّع HMAC** يحوي `tenant_id, user_id, role, exp`. لا يقرأ أي جدول بيانات (RLS-07/08).
3. كل دالة `api.*` تفتح السياق عبر `private.enter_ctx(ctx)`: تتحقق من التوقيع والانتهاء **وحالة المستخدم/الدور الحالية** (فتعطيل مستخدم أو خفض دوره يوقف ctx القديم فوراً — ISO-D7/D8)، ثم تضبط `app.tenant_id` لهذه المعاملة فقط.
4. سياسة `tenant_isolation` (USING + WITH CHECK) على كل جدول → بدون ctx = صفر صفوف.
5. المهام المجدولة تستعمل `app_jobs` وتحصل على ctx لكل عميل **READY ولديه الميزة** فقط (ISO-F5/F6).

### إثبات عدم القراءة/التعديل بين العملاء (اختبارات تنفيذية، كلها ناجحة)
| المجموعة | ما تثبته |
|---|---|
| ISO-A1..A7 | دور التطبيق لا يقرأ/يكتب `core.*` مباشرة، لا يقرأ مفتاح التوقيع، لا يصنع ctx. |
| ISO-B1..B7 | سرّ خاطئ / سرّ عميل آخر / مستخدم عميل آخر / بوت مجهول / عميل غير جاهز → **لا سياق**. |
| ISO-C1..C7 | ctx معدَّل (tenant أو دور)، فارغ، مقطوع، منتهٍ → مرفوض. |
| ISO-D1..D8 | كل عميل يرى حملاته فقط، لا يُنشئ على حساب غيره، حدود الميزانية والأدوار تعمل، المستخدم المعطّل يتوقف فوراً. |
| ISO-E1..E11 | الأخطاء/المعرفة معزولة؛ المعرفة العامة تُنقّى (تمنع معرّفات/إيميلات/توكنات). |
| ISO-F1..F8 | حسابات المهام لا تستطيع حل مستخدمين، ولا تكتب إلا للعميل الصحيح؛ لقطات التقارير لا تختلط. |
| RLS-01..09 | بدون tenant → صفر؛ INSERT لعميل آخر مرفوض (WITH CHECK)؛ UPDATE/DELETE لصفوف الآخرين لا يؤثر. |
| PART-11 | RLS يعمل عبر كل أقسام الأشهر. |

**قيد معروف:** مالك الجداول `app_owner` ليس superuser ويخضع لـ FORCE RLS، لكن مدير قاعدة البيانات (superuser) يتجاوز RLS بطبيعته. لذلك: حساب superuser لا يُعطى لأي خدمة، ويُستعمل فقط للتثبيت اليدوي (انظر المخاطر RR‑01).

## 4) القيود الناقصة التي أُكملت

**`active_config_version`:** FK مركّب `(tenant_id, active_config_version) → config_versions(tenant_id, version)` من نوع `DEFERRABLE INITIALLY IMMEDIATE` (يسمح بإنشاء العميل ثم نسخة الإعداد ضمن معاملة واحدة). اختبارات CON‑09a/b/CON‑12: لا يمكن الإشارة لنسخة غير موجودة أو لعميل آخر، ولا READY بدون نسخة فعّالة.

**الأقسام الشهرية** (`40_partitions.sql`): `report_snapshots` و`error_log` مقسّمة شهرياً مع قسم DEFAULT.
- `api_admin.ensure_partitions(months_ahead, months_back)` — idempotent؛ ينقل الصفوف العالقة في DEFAULT إلى قسمها الصحيح (PART‑01, 05, 06).
- `api_admin.partition_health()` — يبلّغ إن غاب قسم الشهر الحالي/القادم أو امتلأ DEFAULT (PART‑02, 04) ← يُربط بتنبيه Telegram.
- `api_admin.drop_old_partitions(months)` — احتفاظ ≥ شهر، ولجداول معروفة فقط (PART‑07..10).
- **التشغيل:** مهمة مجدولة يومية (pg_cron أو n8n) تستدعي `ensure_partitions(3, 0)` + `partition_health()`. هذه مهمة إعداد (انظر القسم 9)، وليست تلقائية حتى تُجدول.

## 5) حماية التوكنات والأسرار (مطبّق ومُختبَر في `design/broker/`)

| الطبقة | التطبيق |
|---|---|
| **أين تُخزَّن** | ليس في القاعدة المركزية (LINT‑12: لا عمود بأسماء token/secret/password). قاعدة/schema منفصل `vault` لا يصله أي دور تطبيقي (LINT‑11). |
| **التشفير** | تشفير مغلّف: مفتاح بيانات DEK عشوائي لكل سرّ، يُغلَّف بمفتاح رئيسي KEK يعيش في بيئة الـ Broker فقط (متغير بيئة/Secret manager)، لا في أي قاعدة ولا في n8n. AES‑256‑GCM. |
| **ربط بالعميل (AAD)** | `tenant_id\|kind\|version\|secret_ref` — نسخ سرّ عميل إلى صف عميل آخر أو نسخة أخرى **يفشل فك تشفيره** حتى مع المفتاح الرئيسي (اختبارات test_cross_tenant / wrong_kind / tamper). |
| **التدوير** | تدوير KEK بإعادة تغليف DEK فقط دون لمس النص المشفّر (test_rotation). تدوير التوكنات نفسها: نسخة جديدة (version+1) ثم تعطيل القديمة. |
| **الصلاحيات** | n8n لا يرى أي سرّ. يطلب من الـ Broker «نفّذ استدعاء X لعميل ctx» والـ Broker يحقن التوكن ويستدعي المنصة ويرجع النتيجة فقط، مع قائمة سماح بالنقاط (endpoints) لكل عميل. |
| **توثيق n8n→Broker** | HMAC‑SHA256 على `timestamp.nonce.body` + نافذة 60 ثانية + منع إعادة الإرسال (replay) (اختبارات Hmac: تعديل الجسم/الوقت/nonce/مفتاح خاطئ/إعادة → مرفوض). |
| **إبعادها عن السجلات** | فلتر إخفاء ثلاثي: أنماط (Telegram/Meta EAA/TikTok 40‑hex/Bearer/`access_token=`/`code=`)، مفاتيح قواميس حسّاسة، وقيم الأسرار الحيّة بالذاكرة (حجب حرفي بأي صيغة)؛ يغطي الرسالة والمعاملات والـ traceback (اختبارات Redaction). وعلى طرف القاعدة: `api.log_error` يطبّق redaction بالـ regex قبل الحفظ (ISO‑E4). |
| **ما لا يغطيه الكود** | حقل `Credentials` في n8n نفسه: لن تُخزَّن فيه أي أسرار منصات (يمرّر n8n ctx فقط)؛ ويُضبط الاحتفاظ ببيانات التنفيذ على الحد الأدنى في النسخة الجديدة. |

## 6) اختبارات الجاهزية لكل عميل (R01–R15 + بوابة READY)

العميل لا يصير `READY` إلا إذا نجحت **كل الفحوصات الإلزامية** وكانت **سارية** (غير منتهية)؛ trigger في القاعدة يمنع حتى `UPDATE` يدوي (READY‑10). فحص منتهٍ → مهمة `sweep_readiness` تحوّل العميل إلى `NEEDS_REVIEW` فيتوقف البوت التفاعلي (READY‑07/09). «warn» لا يُحسب نجاحاً (READY‑04).

| الكود | ما يُفحص | ينطبق على | صلاحية النتيجة |
|---|---|---|---|
| R01 | سجل العميل سليم (حالة، ميزات، منطقة زمنية) | الكل | 7 أيام |
| R02 | توكن بوت تيليجرام صالح (getMe) | الكل | 24 ساعة |
| R03 | webhook مضبوط وسليم (بـ secret_token، بلا أخطاء معلّقة) | الكل | ساعة |
| R04 | المالك مسجّل + رسالة ذهاب/عودة ناجحة | الكل | 7 أيام |
| R05 | اتصال TikTok صالح (توكن + advertiser) | من لديه ميزة tiktok | 24 ساعة |
| R06 | اتصال Meta صالح وغير قريب الانتهاء | من لديه ميزة meta | 24 ساعة |
| R07 | صلاحيات Meta الممنوحة كافية (ads_management/ads_read…) | meta | 24 ساعة |
| R08 | الحساب الإعلاني مقروء ومربوط بهذا العميل فقط | الكل | 24 ساعة |
| R09 | الوصول للصفحة/إنستغرام | meta | 24 ساعة |
| R10 | **اختبارات العزل** (عميل آخر لا يرى/لا يعدّل بياناته) | الكل | 7 أيام |
| R11 | **إنشاء آمن (dry-run/PAUSED) ناجح بدون حملة حقيقية** | الكل | 7 أيام |
| R12 | القراءة والتقارير تعمل (لقطة تقرير) | الكل | 24 ساعة |
| R13 | اختبارات معالجة الأخطاء (تسجيل، تصنيف، تنبيه) | الكل | 7 أيام |
| R14 | لا أسرار في السجلات ولا في بيانات n8n | الكل | 24 ساعة |
| R15 | نسخة إعداد معتمدة + خطة رجوع موجودة | الكل | 7 أيام |

> الفحوصات R01–R15 معرّفة في القاعدة مع بوابة READY المُختبَرة. **منطق تنفيذ كل فحص ضد Telegram/Meta/TikTok الحقيقية يحتاج برمجة (workflow/Broker)**، وهو غير موجود بعد.

## 8) خطة الاختبارات المقبولة (Acceptance) — ما تثبته وأين

| المعيار | الحالة | الدليل / ما ينقص |
|---|---|---|
| **سلامة النظام** (لا يفتح باب لتجاوز) | مُثبت على مستوى القاعدة | LINT‑01..12 + ISO‑A. ينقص: اختبار اختراق للـ Broker بعد برمجته. |
| **عدم اختلاط العملاء** | مُثبت على مستوى القاعدة | ISO/RLS/CON/PART‑11 + تزامن. ينقص: اختبار طرف‑لطرف عبر n8n (بوتان حقيقيان + عميلان تجريبيان). |
| **عدم تكرار إنشاء الحملات** | مُثبت على مستوى القاعدة (بما فيه التزامن) | IDEM‑01..14. حالة «غامضة» (انقطع الاتصال بعد إرسال الطلب للمنصة): الحالة `needs_manual_check` بعد 10 دقائق ولا إعادة إنشاء صامتة (IDEM‑08). ينقص: ربط الـ Broker بـ `external_request_id` للمنصة حيث تدعمه. |
| **انتهاء التوكن** | جزئي | READY‑07: انتهاء الفحص يوقف العميل. R05/R06 تفحص صلاحية التوكن. **ينقص:** مهمة يومية تجدد/تنبّه، وتعامل الـ Broker مع 401/190/40105 (يعلّم الاتصال `expired` ويوقف الإنشاء ويرسل تنبيه). |
| **فشل واجهات المنصات** | غير مبرمج بعد | المصمَّم: تصنيف خطأ (مؤقت/دائم/صلاحية/رصيد/رفض سياسة)، retry بـ backoff للمؤقت فقط، **لا retry لعمليات الإنشاء** بدون idempotency، circuit breaker لكل منصة/عميل، رسالة واضحة للعميل. يُختبر ببوابة محاكاة (mock) تُرجع 429/500/timeout/401. |
| **الأسرار** | مُثبت للمكوّن | 22 اختبار Broker. ينقص: اختبار «grep» على سجلات الخدمة الحقيقية بعد التشغيل. |

**اختبارات طرف‑لطرف المطلوب كتابتها (E2E)** بعد برمجة الـ Broker وworkflow المركزي، على **عميلين تجريبيين** (بحسابات إعلان اختبارية/وضع PAUSED):
1. رسالة من مستخدم عميل B إلى بوت A → لا رد/لا بيانات.
2. إنشاء حملة بنفس مفتاح الطلب مرتين وبالتوازي → حملة واحدة.
3. إبطال توكن Meta/TikTok لعميل → يتوقف إنشاؤه فقط، يصله تنبيه، ولا يتأثر الآخر.
4. محاكاة 429/500/timeout من المنصة → سلوك retry/توقف كما صُمّم.
5. إيقاف قاعدة البيانات 60 ثانية → لا حملات مكررة ولا فقدان تحديثات (claim_update).
6. تسريب مقصود: حقن توكن في رسالة خطأ → لا يظهر في أي سجل.

## 10‑أ) النسخ الاحتياطي وخطة الاستعادة (شرط قبل تشغيل أي خدمة)

**القاعدة:** لا تُشغَّل أي خدمة (Broker، n8n، Workflows) على أي بيئة قبل أن يمرّ تمرين الاستعادة أدناه بنجاح على تلك البيئة.

| العنصر | dev | staging |
|---|---|---|
| قاعدة التطبيق | `pg_dump` يومي + قبل كل ترقية مخطط | نسخ يومي + WAL (PITR) إن توفّر |
| قاعدة `vault` | نسخة منفصلة مشفّرة (age/GPG) بمفتاح مختلف | نفسه، في حاوية تخزين منفصلة |
| KEK (المفتاح الرئيسي) | **لا يُخزَّن مع النسخ**؛ نسخة مشفّرة بيدك خارج المشروع | نفسه |
| ملفات n8n (Workflows) | في Git (مصدر الحقيقة) | في Git + تصدير |
| الاحتفاظ | 7 أيام | 14 يوماً يومية + 8 أسابيع أسبوعية |
| الهدف | RPO ≤ 24 ساعة، RTO ≤ ساعة | RPO ≤ 5 دقائق (إن PITR)، RTO ≤ ساعة |

**تمرين الاستعادة (يُنفَّذ في P2 ويُكرَّر بعد كل تغيير جوهري):**
1. أخذ نسخة من قاعدة فيها بيانات اختبار (عميلان وهميان).
2. إنشاء قاعدة فارغة جديدة، واستعادة النسخة عليها.
3. تشغيل الـ 205 اختباراً + مقارنة عدد الصفوف والـ checksums.
4. استعادة `vault` وفك تشفير سرّ تجريبي بالـ KEK المحفوظ منفصلاً (يثبت أن النسخة قابلة للاستعمال).
5. محاكاة الفقد: حذف قاعدة dev كاملة ثم الاستعادة وقياس الزمن فعلياً (RTO) وتوثيقه.
6. النتيجة تُكتب في `ops/restore-drill-log.md`؛ فشل أي خطوة = لا تشغيل.
