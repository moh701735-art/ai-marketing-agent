## 3. فحص Meta وTikTok

- إصدار Graph `v20.0` ثابت داخل أكثر من 40 عقدة في كل بوت. تغيير الإصدار يعني تعديل كل عقدة في كل بوت.
- إنشاء الحملة مقسوم على عقد: حملة ← تحضير مجموعة ← مجموعة ← Creative ← إعلان. تحضير المجموعة يحدد الصفحة بالاسم من نص المستخدم (حلّ جزئي مضاف لعلي فقط)، والمعرف الفعلي غير مستخدم أولاً.
- التحقق من الصفحة وInstagram: Instagram يُجلب عبر صفحات المستخدم، وفشله يُهمل بصمت (`igId` يصير فارغاً) بدل أن يفشل الفحص.
- التوكنات: Meta عبر credential نوع `facebookGraphApi` لكل بوت. TikTok عبر `httpHeaderAuth` ثابت واحد لكل بوت. لا يمكن تغييره بتعبير (expression) داخل العقدة.
- قراءة التقارير: موجودة (تقرير الأداء كل ساعة + لقطات بالساعة بجدول لكل عميل).
- Webhooks: واتساب وChallenge وOAuth موجودة بالرئيسي وعلي وحسن. غير موجودة بمسلم واحمد.

## 5. ما يجب تحويله لوحدات مشتركة

أولوية 1 (أعلى تكرار وأعلى خطر):
1. **إرسال الرد (تليجرام/واتساب)**: Sub-workflow واحد `shared/send-reply` يستخدم credential تليجرام بدل التوكن بالـ URL.
2. **التحقق قبل التنفيذ + اكتشاف المنصة + هوية العميل** (`تحقق قبل التنفيذ`).
3. **وحدة Meta**: تحضير الاستهداف، اختيار الصفحة بالمعرف، Creative، سقف الرسالة.
4. **وحدة TikTok**: تجهيز الحملة/المجموعة/الإعلان، تحديد الجمهور.
5. **صياغة الرد النهائي وترجمة الأخطاء** (`fr()` + `metaErr`).

أولوية 2: التقارير والمراقبة (سقف التكلفة، الرصيد، الاستمارات، الطعون)، قاعدة المعرفة.

الآلية المقترحة: Execute Workflow Trigger في Workflow مشترك واحد لكل وحدة، وتمرير `client_config` (من جدول واحد) كمدخل. كل بوت عميل يبقى رقيقاً: Trigger + تحميل إعدادات العميل + استدعاء الوحدات.

## 6. إعداد عميل جديد دون نسخ أخطاء السابق

- جدول واحد `clients` (client_id، الحالة، حساب Meta، صفحة، Instagram، TikTok advertiser، المنطقة الزمنية، العملة، chat id، اسم credential) بدل جدول لكل عميل.
- المنطق لا يُنسخ. الإعدادات فقط. الاعتماد على Sub-workflows.
- credentials تُربط يدوياً لكل عميل (لا يمكن إنشاؤها عبر MCP)، والفحص يتأكد من صلاحيتها.
- حالات العميل: INITIALIZING ← CONFIGURATION_REQUIRED ← CONNECTING ← TESTING ← READY / FAILED / NEEDS_REVIEW.
- ملاحظة للتنفيذ: `authentication` ثابت بالعقدة، فتوكن TikTok لكل عميل يتطلب credential مستقل. الخيار البديل: كتابة التوكن بجدول وقراءته بـ Header يدوي (بدل credential)، وهو أضعف أماناً لأنه يخزن التوكن بجدول. أوصي بإبقاء credential لكل عميل.

## 7. قاعدة المعرفة واختبارات الانحدار

- قاعدة المعرفة: جدول `knowledge` (العنوان، النطاق: عام/عميل، المصدر، التاريخ، الإصدار، النص). بحث بالكلمات المفتاحية أولاً، وRAG (متجه) لاحقاً إذا توفر Vector Store. المعرفة العامة مفصولة عن بيانات العميل. لا تخزّن توكنات أو كلمات مرور.
- سجل الحلول: جدول `solutions` (البصمة، المنصة، الرمز، السبب، الحل، حالة التحقق، تاريخ). لا يُضاف حل إلا بعد نجاح اختبار.
- اختبارات الانحدار: Workflow اختبار يعمل بـ Manual/Schedule، بوضع آمن (حملة `PAUSED`، ميزانية دنيا أو Dry-run بلا استدعاء Create)، يغطي القائمة الموجودة بالمرحلة 8.
